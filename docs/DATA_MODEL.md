## How the pieces relate

There are three groups of tables and one thing that ties them together.

**Identity** is `users`, `sessions` and `oidc_accounts`. A user is a person with an email
address and, optionally, a password. A session is a row keyed by the hash of a bearer token.
An OIDC account links a provider's subject identifier to a local user.

**Tenancy** is `organizations` and `memberships`. An organization is what the interface calls
a _property_ -- a home, a church, a small business. A membership joins a user to an
organization and carries the role that decides what they may do there. `user_roles` is a
second, non-authoritative copy of that role; see the trap noted below.

**Content** is everything else, and every one of those tables carries `organization_id`.
`items` is the centre of it. An item points at a `location`, a `category` and optionally a
`gear_profile`; it accumulates `item_events`, `photos` and `documents`. `tags` and `item_tags`
model the many-to-many between items and labels. `wishlist_entries` sit beside items rather
than inside them, and each entry accumulates `savings_contributions` and `price_observations`.

```
users ──< memberships >── organizations ──< everything below
  │                            │
  ├──< sessions                ├──< locations ──┐ (self-referencing parent)
  └──< oidc_accounts           ├──< categories  │
                               ├──< tags <──┐   │
                               ├──< items ──┴───┘
                               │     ├──< item_events
                               │     ├──< photos
                               │     ├──< documents
                               │     └──< item_tags
                               ├──< wishlist_entries
                               │     ├──< savings_contributions
                               │     └──< price_observations
                               ├──< gear_profiles
                               └──< user_roles  (mirror of memberships.role)
```

Two arrows in that diagram are weaker than they look. `items.gear_profile_id` is not a
foreign key, and `item_tags.tag_id` is not one either. Both are deliberate and both are
explained under [Design decisions](#design-decisions).

## Multi-tenancy

Every content table carries a `organization_id` column, and that column is the tenant
boundary. It is never taken from a request body. The server reads it from the verified URL
path, checks membership server-side, and only then touches a row -- see `requireOrgAccess` in
[`server/auth/access.ts`](../server/auth/access.ts) and the generic router in
[`server/app.ts`](../server/app.ts), which strips `id` and `organizationId` out of any PATCH
body before applying it.

Three tables are outside the boundary because they precede it: `users`, `sessions` and
`oidc_accounts` belong to a person, not to a property.

## Identity and tenancy tables

Column types are the SQLite storage classes the DDL declares. Every timestamp is TEXT; the
convention across the codebase is an ISO 8601 string, with the database defaults falling back
to SQLite's `current_timestamp` format (`YYYY-MM-DD HH:MM:SS`, UTC, no `T` and no zone
suffix). Those two formats are not identical, and code that parses `created_at` should be
tolerant of both.

| `name`          | TEXT | no   | --                  | Display name                                                               |

None of these are database constraints. Every one of them is a TEXT column with no `CHECK`,
and the values are enforced by the Zod schemas at the API boundary and by TypeScript in the
browser. A row written by hand with `sqlite3` can hold anything.

| Type                 | Values                                                                                                                                    | Where it lives                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| `UserRole`           | `ADMIN`, `MANAGER`, `VIEWER`, `CONTRIBUTOR`                                                                                               | `memberships.role`, `user_roles.role` |
| `ItemCondition`      | `NEW`, `GOOD`, `FAIR`, `POOR`, `DAMAGED`, `DISPOSED`                                                                                      | `items.condition`                     |
| `PurchaseSource`     | `STORE`, `ONLINE`, `DONATION`, `OTHER`                                                                                                    | Client type only; no server column    |
| `DepreciationMethod` | `NONE`, `STRAIGHT_LINE`, `DECLINING_BALANCE`, `MANUAL`                                                                                    | `items.depreciation_method`           |
| `ItemStatus`         | `IN_POSSESSION`, `LOANED`, `IN_REPAIR`, `BROKEN`, `SOLD`, `LOST`                                                                          | Derived, never stored                 |
| `ItemEventType`      | `ACQUIRED`, `LOANED_OUT`, `RETURNED`, `BROKE`, `SENT_FOR_REPAIR`, `REPAIR_COMPLETED`, `SOLD`, `LOST`, `MOVED`, `VALUE_REASSESSED`, `NOTE` | `item_events.type`                    |
| `WishlistPriority`   | `LOW`, `MEDIUM`, `HIGH`                                                                                                                   | `wishlist_entries.priority`           |

Two further closed sets are not declared as named TypeScript types but behave the same way:
`organizations.type` accepts `home`, `church`, `small_business` or `other`, and
`documents.type` accepts `RECEIPT`, `WARRANTY`, `APPRAISAL`, `INSURANCE_POLICY` or `OTHER`.

`ItemStatus` deserves a note of its own. It is a separate axis from `ItemCondition`: a drill
can be in `GOOD` condition _and_ `LOANED`. Conflating the two is why an earlier model could
not express a loan at all.

## The permission matrix

Ten permissions, four roles. `Yes` means the role holds the permission.

| Permission              | ADMIN | MANAGER | CONTRIBUTOR | VIEWER |
| ----------------------- | :---: | :-----: | :---------: | :----: |
| `canViewItems`          |  Yes  |   Yes   |     Yes     |  Yes   |
| `canAddItems`           |  Yes  |   Yes   |     Yes     |   no   |
| `canEditItems`          |  Yes  |   Yes   |     no      |   no   |
| `canDeleteItems`        |  Yes  |   no    |     no      |   no   |
| `canArchiveItems`       |  Yes  |   Yes   |     no      |   no   |
| `canManageLocations`    |  Yes  |   Yes   |     no      |   no   |
| `canManageCategories`   |  Yes  |   Yes   |     no      |   no   |
| `canManageUsers`        |  Yes  |   no    |     no      |   no   |
| `canManageOrganization` |  Yes  |   no    |     no      |   no   |
| `canExportData`         |  Yes  |   Yes   |     no      |  Yes   |

In prose: **ADMIN** holds all ten. **MANAGER** holds seven -- everything except deleting
items, managing users and managing the property itself; a manager can archive but not delete.
**CONTRIBUTOR** holds two, view and add, and notably cannot export. **VIEWER** holds two, view
and export.

The matrix exists twice, on purpose. [`src/lib/auth/permissions.ts`](../src/lib/auth/permissions.ts)
is the browser copy and decides what to _show_; [`server/auth/access.ts`](../server/auth/access.ts)
is the server copy and decides what is _allowed_. They are not a shared import, because sharing
one module invites the assumption that a client-side check is a control -- which is exactly the
mistake the local-only tier made. Keeping them honest is a test:
[`tests/server/auth.test.ts`](../tests/server/auth.test.ts) sorts both matrices and asserts
they are equal for every role, so a change to one that is not made to the other fails the
suite. If you add a permission, edit both files and the test will tell you whether you did.

Which permission each API collection demands for reads and writes is documented in
[API.md](./API.md#tenant-scoped-collections).

## Design decisions

**Status is derived, not stored.** There is no `status` column on `items`. `deriveStatus` in
[`src/lib/lifecycle/index.ts`](../src/lib/lifecycle/index.ts) folds the event log in
chronological order and returns the current state; `SOLD` and `LOST` are terminal, and `MOVED`,
`VALUE_REASSESSED` and `NOTE` do not transition anything. The consequence worth knowing is that
a mistake is corrected by appending another event, never by rewriting history.

**`items.gear_profile_id` is not a foreign key.** The value is either a stored
`gear_profiles.id` or a catalogue id derived from brand and model, of the form
`catalogue:dewalt::dcd791d2` -- lowercased, non-alphanumerics stripped, the two halves joined
by `::`. Catalogue rows are never in the database, so a constraint here would reject exactly
the links the catalogue exists to create.

**Catalogue gear profiles are never stored.** They ship in the bundle and merge at read time,
with a USER profile winning over a CATALOGUE one for the same brand and model. Persisting them
would copy a read-only dataset into every tenant and turn a catalogue update into a migration.

**Specs are label/value pairs, not typed columns.** A cordless drill, a rack switch and a
camera body share almost no spec fields. A typed record would grow a new optional column for
every product type anyone ever added, which is a vendor module wearing a different hat. So
`gear_profiles.specs` is JSON text holding an array of `{ label, value, unit? }`.

**`savings_contributions` and `price_observations` are append-only.** Neither wishlist entries
nor items carry a running total. The total is summed from the rows. That keeps one source of
truth, makes "where did this number come from" answerable, and makes a correction another row
rather than an edit.

**`memberships.role` is authoritative; `user_roles` is a mirror.** This is the trap in this
schema. `requireOrgAccess` reads `memberships.role` and nothing else. `user_roles` exists so
the browser-side `UserRoleAssignment` shape round-trips, and it is writable through the
`user-roles` collection route -- which means it is entirely possible to write `ADMIN` into
`user_roles` and change nobody's actual access. If you are debugging why someone cannot do
something, look at `memberships`.

**`users.password_hash` is nullable.** Null means the account was created through an identity
provider and has no password to check. Login handles that case explicitly and says so, rather
than returning an "incorrect password" the person could never satisfy.

**`sessions` stores only the SHA-256 of the token.** The token itself is never written down.
A leaked database therefore does not hand over usable sessions. SHA-256 rather than scrypt is
correct here: the token is 256 bits of entropy the server generated, not a guessable secret a
human chose, so there is nothing to slow an attacker down over.

**`oidc_accounts` links on `(provider, subject)`, never on email alone.** An email address can
change hands, and a provider that does not verify addresses would otherwise let somebody claim
an existing account simply by asserting its address. Auto-linking an OIDC identity to an
existing local account by email happens only when the provider marks the address verified;
otherwise the attempt is refused.

**Migration is hand-written idempotent DDL.** `migrate()` in
[`server/db/index.ts`](../server/db/index.ts) executes a list of
`CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` statements, preceded by
`PRAGMA foreign_keys = ON` because SQLite has foreign keys off by default and every cascade
above depends on it. drizzle-kit is not a runtime dependency. Because `IF NOT EXISTS` does
nothing to a table that already exists, added columns need their own path:
`addColumnIfMissing` reads `PRAGMA table_info` first, since SQLite has no
`ADD COLUMN IF NOT EXISTS` and running the `ALTER` twice is an error. Today that mechanism
carries exactly one column, `items.gear_profile_id`. This stands in for a migrations directory
until the schema starts changing often enough to need one.

## Client and server divergences

The browser-side types in [`src/types/index.ts`](../src/types/index.ts) and the tables do not
line up exactly. The two that will bite first:

**Client `Item.tags` is `string[]`; the server uses the `item_tags` join table.** The `items`
table has no tags column. The write schema for the `items` collection does not include `tags`,
so a tag array sent in a POST body is silently dropped, and the client normalises a returned
item with `tags: item.tags ?? []`. A join table was chosen over a JSON column so tags are
queryable. Worth stating plainly: as of this writing nothing reads or writes `item_tags`, so
per-item tags do not round-trip through the API at all. The `tags` collection itself works;
it is the item-to-tag association that has no wire representation.

**Client `Photo` has no `organizationId`; the server table does.** Locally a photo is scoped by
the item it hangs off. Over the wire it needs its own tenant column, or the access guard would
have to join through `items` on every request just to decide whether the caller may see a row.
The server fills the column from the verified path, so a client that omits it is correct.

Four smaller ones, for completeness:

| Client type                                        | Divergence                                                                                                                                           |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Item.purchaseLocation`, `Item.purchaseSourceName` | No corresponding columns and not in the write schema, so both are dropped in server mode                                                             |
| `Membership`                                       | Has no `role` field, although `memberships.role` exists and is returned by the API                                                                   |
| `Session`                                          | Has `token` and `rememberMe`; the table has neither. The API provider returns an empty token string, because the real session is the httpOnly cookie |
| `GearProfile`                                      | Has `source`, `licence` and `sourceName`; none are columns. Stored rows are `USER` by construction and catalogue metadata belongs to the catalogue   |
